# 20 — Chown the tree to 99:100 and normalise permissions

Resolved: 2026-08-03

## Question

Nothing to decide — [09](09-unify-uid-gid.md) settled the values. This is the
execution: bring the files already on disk into line with `PUID=99`, `PGID=100`,
`UMASK=002` before any of the three divergent services is adopted.

Three services write as something other than 99:100 today, and their files are
what this ticket fixes:

| service | current uid:gid | what it owns |
|---|---|---|
| `qbittorrent` | 1001:1001 | `/mnt/user/Media/downloads` and its own appdata |
| `plex` | 1000:1000 | `/mnt/user/appdata/plexmediaserver` (20G) |
| `gluetun` | 1000:1000 | its own appdata, if any |

**Not just a chown.** All three are Portainer-managed compose stacks, and they
keep running as their old uid until something changes their definition. Chowning
their appdata to 99 while they still run as 1000/1001 leaves them unable to
write their own config. So this ticket **also edits the two Portainer stacks**
to the new values and redeploys them, in the same window. The five
unraid-template services are already 99:100; their `UMASK` and `TZ` are stale
but harmless, and they pick up the new values when they adopt.

**HITL** — per the map's Box access note, this runs as a hand-off. Write the
whole thing as one copy-pasteable checklist for the Unraid Web UI terminal, with
output to paste back.

### Shape of the checklist

1. **Snapshot first.** Ownership and mode counts under `/mnt/user/Media` and the
   three appdata dirs, so the after-state can be compared to something.
2. **Stop every container.** All eight workloads plus Portainer's own.
3. **Chown.** Prefer per-disk paths — `/mnt/disk1..6/Media`, plus `/mnt/cache`
   if anything lives there — over `/mnt/user/...`; shfs makes a recursive chown
   over 39 TB far slower than the same work done disk by disk. Run it under
   `nohup` with a log: the Web UI terminal closing must not kill a job this
   long.
4. **Chmod the media tree only** — dirs 775, files 664, matching `UMASK=002`.
   **Do not blanket-chmod appdata**: it is application state, some of it
   expects its own modes, and 09 only needs the *ownership* fixed there.
5. **Update the two Portainer stacks** — plex, and gluetun+qbittorrent — to
   `PUID=99`, `PGID=100`, `UMASK=002`, `TZ=America/Vancouver`. Redeploy.
6. **Start everything and verify.** Each UI loads; qbittorrent still lists its
   torrents and has not started re-checking; sonarr/radarr can still see
   `/downloads`; **plex still hardware-transcodes** — play something that forces
   a transcode and confirm the dashboard says `(hw)`. Plex's `/dev/dri` access
   depends on the container user's groups and it has just changed user, so this
   is the check most likely to fail.

The answer records: how long the chown actually took, anything that did not come
back cleanly, and whether plex kept hardware transcoding.

### Not blocked

Depends on nothing — not Komodo, not the repo layout, not the remote. It only
has to happen **before plex, gluetun or qbittorrent is adopted**, because those
three cannot read their own appdata until it does. Adoption of the five
already-99:100 services does not wait on it.

## Resolution

Rolled into [19](19-secret-hygiene-on-the-box.md) and executed there — the two
tickets turned out to be one problem. 19 found that the box's `chmod -R 777`
was a **stopgap for exactly what this ticket fixes**: `UMASK=022` creates 755
directories, and rb (uid 1001, gid 100) cannot rename or delete inside them.

Done, and verified after:

- **`chown -R 99:100`** on `plexmediaserver` (155,334 paths off-uid),
  `qbittorrent` (150), `gluetun`, `transcode` — all now **0**.
- **Both Portainer stacks edited and redeployed** in the same window, so nothing
  ran as its old uid against a chowned tree. plex `1000:1000` → `99:100`,
  qbittorrent `1001:1001` → `99:100`, gluetun `1000:1000` → `99:100`, and
  `UMASK=002` added to plex and qbittorrent.
- The 777 is gone tree-wide; see 19's table.

**It ran AFK, not HITL.** This ticket predates SSH being proven, and its
paste-back checklist was unnecessary — the map's Box access note supersedes it.

### Three things this ticket had wrong

- **`/dev/dri` is not a risk.** `renderD128` is `crwxrwxrwx`, so group
  membership is irrelevant. Plex's own log confirms it under the new uid:
  `adding /dev/dri/renderD128 to group group1sck`, `permissions for
  /dev/dri/card0 are good`. This also settles the check
  [23](23-migrate-plex.md) carries.
- **"Their `UMASK` is stale but harmless"** — the opposite. `UMASK=022` on the
  five unraid-template services is the **root cause** of the 777, because they
  are what writes media.
- **There is no compose binary on the box.** Only `docker` and `buildx`;
  Portainer and Komodo each run compose inside their own container. The stacks
  were recreated by driving the box's daemon over `DOCKER_HOST=ssh://root@tower`
  with the compose file streamed over stdin, so no copy of the WireGuard key
  landed anywhere new. Worth knowing for [23](23-migrate-plex.md),
  [24](24-migrate-download-stack.md) and [25](25-retire-portainer.md).

### Left over

The five *arr templates now say `UMASK=002`
(`/boot/config/plugins/dockerMan/templates-user/my-*.xml`, `.bak-19` alongside),
but **a template edit does not recreate a running container** — the five still
run `022` until each is re-applied in the Unraid UI, or until
[21](21-migrate-arr-stacks.md) and [22](22-migrate-calibre.md) adopt them from
git. Until then new *arr-created directories land 755 again. The tree is
correct today; this is about keeping it that way.
